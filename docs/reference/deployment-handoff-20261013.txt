USING THE EXISTING LOCAL CLI AGENT
The local CLI remains local. It must explicitly use SSH/SFTP for remote work.
The supplied worker_client.py creates a single-use ticket, connects to this one
target, runs the operation, and revokes the ticket. It never prints the ticket.
It uses the existing trusted Warpgate key in ~/.ssh/known_hosts and rejects
untrusted server keys. Supply a valid Warpgate API token through a protected
--token-file, WARPGATE_API_TOKEN environment variable, or its hidden prompt.
API token creation and user rights remain governed by Warpgate.

Example local setup (from infrastructure/ign04-site-agent-jail):
  python3 -m venv /tmp/site-agent-client-venv
  /tmp/site-agent-client-venv/bin/pip install -r requirements.txt

Example commands:
  /tmp/site-agent-client-venv/bin/python worker_client.py --command 'id; pwd; hostname'
  /tmp/site-agent-client-venv/bin/python worker_client.py --upload ./input.zip /workspace/work/input.zip
  /tmp/site-agent-client-venv/bin/python worker_client.py --download /workspace/work/result.zip ./result.zip
Commands begin in /workspace/work. Transfer destinations are explicit.
Read /workspace/ignProjects/AGENTS.md before project work. Clone/copy the required
project into writable work storage; do not attempt edits in the read-only mount.

Alternatively, obtain a scoped ticket for this target from Warpgate and use:
  ssh -p 2222 -l 'ticket-<ticket-secret>' warp.wbinfra.com 'cd /workspace/work && id && pwd'
  sftp -P 2222 -o 'User=ticket-<ticket-secret>' warp.wbinfra.com
The ticket is the SSH username credential; a dummy password such as "ticket"
works for the SSH password challenge. Use a new ticket for each connection.
Avoid recording ticket secrets in scripts, history, reports or logs.

ISOLATION LIMITS / REMAINING WORK
This is a constrained workspace, not a guarantee against escape or host harm.
LXD and Docker share IGN04's kernel. The jail is unprivileged and Docker rootless,
but kernel/runtime vulnerabilities remain possible. Storage has NO per-worker
quota: filling persistent volumes can pressure shared storage. Logs are bounded.
The existing jail network blocks private destination ranges and allows public
HTTP/HTTPS plus infrastructure DNS/DHCP. It is not an air gap; public endpoints
and data exfiltration are not universally prevented. No production IPC was tested.
CPU/memory/PID limits constrain this worker, not all existing jail containers.
The worker has no SSH forwarding, but an allowed shell can still run programs;
network policy, mounts and permissions determine their actual reach.
A separate VM provides a stronger boundary if hostile/untrusted workloads are
expected. Native Ignition lab execution has not been validated in this worker.
Ticket expiry/revocation is not proven to kill active sessions/background jobs.
Do not treat ticket expiry or the client's local timeout as a job kill switch.
No Cunner inputs, commissioning workflow, production deployment or WAVE merge
was performed as part of this setup. Infrastructure has no remaining blocker.
